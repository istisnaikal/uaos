# ADR-0018 evidence: chunk put and flush cost on the reference machine (2026-10-15)

**Machine:** the reference machine (Windows 10, Ryzen 5600X, solid-state drive), release build.
**Command:** `journal-ack-bench`, from branch `p3/a1-chunk-durability`. The nightly
`ack-latency` job produces the Linux and macOS rows on CI runners.

| Series (4 KiB chunks) | n | p50 | p95 | p99 | p99.9 |
|---|---|---|---|---|---|
| `chunk-put`: strict, both files flushed before return | 1,000 | 2.41 ms | 2.80 ms | 3.11 ms | 11.3 ms |
| `chunk-put-balanced`: handed to the OS, temporary and rename **(shipped)** | 32,000 | 1.64 ms | 1.82 ms | 2.10 ms | 12.4 ms |
| `chunk-put-balanced`: created in place under the final name (measured, rejected) | 32,000 | 0.89 ms | 2.56 ms | 7.54 ms | 13.7 ms |
| `group-flush-chunks`: one flush covering 64 records, each with its own new chunk (128 files, then the segment) | 500 | 50.9 ms | 60.0 ms | 65.5 ms | 132 ms |
| `balanced`: journal append, for reference | 20,000 | 4.2 µs | 5.4 µs | 29.2 µs | 67.6 µs |

**What this shows.**
- **Removing the flush helps, but not enough.**
  - Removing the flush from the put path cuts p99 from 3.1 ms to 2.1 ms on this machine.
  - The rest is file creation, two files per chunk, and Windows' file-system filters.
  - ADR-0018's target of p99 ≤ 0.5 ms is **not met** on this platform.
- **Creating in place trades the wrong way.** It halves p50 but triples p99. The overhead SLO is
  judged at p95 and p99, so the rename stays.
- **Today the request that triggers a flush pays for it.**
  - Each file flush costs about 0.4 ms here. A window holding 64 new chunks therefore takes
    about 51 ms to flush.
  - The flush runs inline in `Journal::append` when the window is due, so the append that
    finds it due waits for the whole flush.
  - Real traffic adds a few chunks per request, not 64 per window.
  - Once the flush moves to its own thread (the WP3.3 state actor), this cost widens the
    effective window W instead of delaying an acknowledgement. Until then it is not off the
    request path.
- **This is ADR-0018 Decision 4's trigger.**
  - One key file per chunk is now a measured cost on the hot path.
  - The follow-up is a per-pocket keystore log, which halves the file count. It changes shred
    semantics (ADR-0007), so it needs its own ADR and a maintainer decision.

## Re-measured after the review fixes (2026-10-16)

Same machine, one session, outside the shared target directory: `2cf78f8` was built first in a
fresh scratch target, then the fixed code in the same one. The fixed binary was checked to
contain the new store code.

| `chunk-put-balanced`, 32,000 puts | p50 | p95 | p99 | p99.9 |
|---|---|---|---|---|
| `2cf78f8` (before the review fixes) | 1.20 ms | 1.69 ms | 1.93 ms | 17.3 ms |
| Fixes, as shipped | 1.14 ms | 1.34 ms | 1.55 ms | 9.4 ms |
| The same binary, second run | 1.14 ms | 1.33 ms | 1.55 ms | 9.8 ms |

**What this shows.**
- **The fixes cost nothing measurable on this path.** The shipped code is within run-to-run
  noise of `2cf78f8`.
- **Read-back of new names.** A put now replaces a pair left by an earlier process only by a
  flushed write (review N1), so it must know whether one exists. The shipped code indexes the key
  files present when the store opens and reads back only names found there. Reading every new
  name back instead measured p50 1.71 ms against 1.65 ms for the index, both built in the shared
  target directory (see below), so the read-back costs about 0.05 ms.
- **The target is still not met.** p99 is 1.55 ms against ADR-0018's 0.5 ms.
- **The 2026-10-15 rows above are suspect.** They were built in the target directory shared by
  several worktrees of the repository. That directory produced a binary of the same code that
  differed byte for byte and measured about 0.5 ms slower. Bench numbers now come only from a
  dedicated target directory.
- **Linux and macOS:** from the nightly `ack-latency` job on CI runners.
